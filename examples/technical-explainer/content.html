Запрос — сообщение, а не вся операция

Веб-запрос просит другую систему вернуть данные или выполнить действие. Ответ сообщает результат обработки этого сообщения.

Когда человек открывает заказ, браузер не читает базу напрямую. Он обращается к API, которое проверяет права, находит нужные данные и формирует ответ. Успешный сетевой обмен ещё не означает успешный бизнес-результат: API может корректно вернуть отказ в доступе.

Вход
Метод, адрес, заголовки и, при необходимости, тело.
Работа
Проверка запроса, применение правил, доступ к состоянию.
Выход
Статус и данные, которые клиент умеет интерпретировать.

Ответственность в иллюстративном сервисе заказов
УчастникВопросЧто делает
БраузерЧто нужно показать человеку?Отправляет запрос, показывает загрузку и обрабатывает ответ.
Пограничный слойКуда направить сообщение?Выбирает сервис, применяет ограничения трафика.
API заказовМожно ли выполнить действие?Проверяет права на конкретный заказ, применяет бизнес-правила.
ХранилищеКакое состояние сохранено?Читает и изменяет записи в пределах своей транзакции.

Такое разделение помогает искать причину сбоя. Если API вернул запрет доступа, исправление сетевого маршрута не изменит права пользователя. Если хранилище недоступно, повторная авторизация тоже не устранит причину.

Один заказ: успешный путь и отказ

Диаграмма последовательности показывает порядок сообщений, а не физическое расстояние между серверами. Ветки обозначают взаимоисключающие варианты одного обращения. Здесь намеренно не нарисованы кеши и очереди: для объяснения проверки доступа они не нужны.

Таймаут оставляет неопределённость

Клиент может перестать ждать раньше, чем сервер закончит работу. Он знает, что ответ не получен вовремя, но не обязательно знает, была ли операция выполнена. Для чтения заказа повтор обычно не создаёт новый заказ. Для отправки платежа тот же подход без дополнительного контракта опасен.

Не путать

«Не получил ответ» и «сервер ничего не сделал» — разные утверждения. Восстановление должно учитывать эту разницу.

  1. 01Клиент

    Ограничить ожидание

    Показать понятное состояние и не блокировать интерфейс бесконечно.

  2. 02Контракт

    Определить повтор

    Заранее описать, допускается ли повтор и как распознать ту же операцию.

  3. 03Сервис

    Сохранить результат

    Если операция имеет эффект, обеспечить согласованное восстановление её результата.

  4. 04Наблюдение

    Связать события

    Использовать идентификатор обращения, не записывая секреты в журнал.

Когда модель нужно расширить

Асинхронная обработка меняет смысл ответа

Если API только приняло задачу в очередь, первоначальный ответ подтверждает приём, но не завершение. Нужно отдельно объяснить статус задачи, способ получения результата, повторную доставку и границу ответственности обработчика.

Начинайте с вопроса читателя. Для проверки прав важен порядок авторизации и чтения. Для задержки — время на каждой границе. Для двойного списания — идентичность операции и правила повторов. Одна и та же система требует разных схем, потому что схемы отвечают на разные вопросы.

Главная мысль

Следите за сообщением, называйте владельца каждого решения и различайте наблюдаемый ответ от фактического состояния операции.
