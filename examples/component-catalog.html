assets/components/api-event-contract.html

Reservation API and creation event

This illustrative contract separates a synchronous outcome from asynchronous delivery. Receiving an event is not required before checkout can use the API response.

Create a hold · POST /v1/reservations

Caller and authorization
Checkout uses a service access token with inventory:reserve. Inventory derives the owning client from the token, not from the JSON body.
Input
Content-Type: application/json; required fields sku (nonempty case-sensitive string) and quantity (integer 1–100). Unknown fields are rejected.
Idempotency
Required Idempotency-Key is scoped to client and endpoint. Completed outcomes are retained for 24 hours. Identical retries replay the status and body; changed input returns 409 idempotency_conflict. Concurrent duplicates wait for the first result.
Retry
On a lost response or a 503, retry with the same key and payload using bounded exponential backoff. A replay does not renew the ten-minute hold; inspect its expiry before payment.
{"sku":"SKU-42","quantity":2}
Response outcomes
HTTP statusMeaningCaller action
201Hold committed; body below.Continue to payment before expiry.
400invalid_request; malformed input or missing key.Correct the request; do not retry unchanged.
401 / 403Invalid credentials / missing scope.Repair service authentication or permissions.
404unknown_sku.Refresh the basket item.
409insufficient_stock or idempotency_conflict.Reduce quantity or resolve key reuse; do not blindly retry.
503temporarily_unavailable; outcome may be unknown to the caller.Retry with the same key to discover the committed outcome.

Successful response:

{"reservation_id":"rsv_1042","state":"active","expires_at":"2026-05-01T10:10:00Z"}

Domain errors use a stable machine code and a human-readable message:

{"code":"insufficient_stock","message":"Only one unit is available."}

Event · inventory.reservation.created.v1

Producer → consumer
Inventory → checkout projection, through an authenticated broker topic restricted to these services.
Publication
The hold and outbox entry commit together. The publisher retries until the broker acknowledges delivery.
Delivery
At least once; duplicates and delayed messages are possible. Consumers deduplicate by event_id and must not treat a delayed creation event as proof the hold is still active.
Compatibility
Consumers tolerate unknown additive fields. Changing the meaning or type of existing fields requires a new event version.
Failure handling
After five failed consumer attempts, quarantine the message for inspection and replay with its original event ID; alert the checkout service owner.

assets/components/as-is-to-be.html

From stock lookup to a timed hold

This illustrative change closes the gap between showing availability and claiming stock. It introduces expiry and retry handling rather than making the checkout process disappear.

AS-IS · Check without holding

  1. Checkout reads available stock.
  2. The customer authorizes payment.
  3. Checkout requests allocation; another customer may have taken the last unit.

Failure: payment may need to be voided because the earlier availability check was not a promise.

TO-BE · Hold before payment

  1. Checkout obtains a ten-minute reservation.
  2. The customer authorizes payment while the hold is active.
  3. Checkout confirms the hold; if it expired, checkout voids the authorization and offers a retry.

Trade-off: abandoned holds temporarily reduce availability and require reliable release.

Transition and observation

Route a checkout through either the old path or the hold path, never both. Both paths must use the same authoritative available-stock calculation. Track confirmation conflicts, expired holds, and payment voids before expanding rollout.

Rollback boundary: stop creating new holds but continue confirming or releasing existing holds until none remain. Simply switching off Inventory would strand reserved units.

assets/components/conclusions.html

Keep the promise and its deadline together

Use a lookup for information and a reservation for a temporary claim. Keep the reservation ID, expiry time, and retry key with the checkout attempt so recovery does not create a second claim.

Key conclusion

A hold protects stock, not the whole purchase. Payment authorization, confirmation, and expiry still need explicit outcomes and recovery paths.

assets/components/definition.html

A reservation is a temporary promise

A stock reservation temporarily removes units from what other checkouts may claim.

It is not a completed sale. Confirmation turns the hold into an allocation; cancellation or expiry returns the units to availability. A payment authorization alone does not confirm the hold.

Claim
An item and a whole-unit quantity.
Deadline
Ten minutes from creation in this example.
Outcome
Confirmed allocation or released stock.

assets/components/details.html

Record the event with the hold

Inventory commits a reservation and an outbox entry in one transaction. A separate publisher sends the entry to the broker, so a broker outage need not roll back an already recorded hold.

Why can the same event still arrive twice?

The broker may accept an event just before the publisher loses its connection. Without an acknowledgement, the publisher cannot distinguish success from failure and sends it again.

The consumer records the event ID with its own state update and ignores a replay of that ID. This handles duplicate delivery; it does not guarantee that every consumer applies every event successfully.

assets/components/goals-scope-actors.html

What stock reservation covers

This example service holds stock while a customer completes checkout. A reservation is not a payment or a shipping instruction.

Goal
Prevent two checkouts from claiming the same available unit.
Success signal
Concurrent requests never reduce available stock below zero; rejected requests identify the unavailable item.
In scope
Create a ten-minute hold, confirm it after payment authorization, and release it on cancellation or expiry.
Out of scope
Payment capture, warehouse picking, and replenishment forecasts.

assets/components/notes.html

A timeout leaves the outcome unknown

The database may commit a hold even if the response never reaches checkout. A network failure alone cannot tell the caller whether stock was reserved.

Reuse the key.

Retry the identical request with its original idempotency key. A new key asks for a new hold and can reserve the same basket twice.

assets/components/requirements-acceptance.html

Observable reservation requirements

These are example acceptance criteria, not evidence that an implementation has passed them.

REQ-01 · Never over-allocate an item

Creation must atomically check available stock and reserve the requested quantity.

  1. AC-01 · Concurrent requests

    Given one available unit and no active holds, when two distinct requests each reserve one unit concurrently, then exactly one succeeds, the other returns 409 insufficient_stock, and available stock becomes zero.

  2. AC-02 · Rejected quantity

    Given one available unit, when a request reserves two units, then no hold or creation event is recorded and available stock remains one.

REQ-02 · A retry must not create a second hold

For 24 hours after the first completed request, an identical request from the same client with the same idempotency key returns its stored outcome.

  1. AC-03 · Lost response

    Given a committed hold whose response was lost, when checkout repeats the same request and key, then the response contains the same reservation ID and stock is not reduced again.

  2. AC-04 · Reused key, changed payload

    Given a completed request, when its key is reused with a different quantity within 24 hours, then the service returns 409 idempotency_conflict and leaves the original hold unchanged.

assets/components/scenario.html

Reserve two units during checkout

Trigger
The customer proceeds from basket to payment.
Preconditions
The checkout service is authenticated; item SKU-42 exists; the requested quantity is two.
Success outcome
One active hold owns two units until confirmation, cancellation, or its ten-minute deadline.
Failure outcome
No partial hold is created. The checkout keeps the basket and explains the rejection.

Main scenario

  1. Checkout submits SKU-42, quantity 2, and a new idempotency key.
  2. Inventory validates the request and checks stock inside the same transaction that creates the hold.
  3. Inventory commits the hold and an outbox record for its creation event.
  4. Inventory returns the reservation ID and expiry time. Checkout shows the payment step.

Alternative paths

A1 · Step 2: insufficient stock
Inventory returns 409 insufficient_stock without creating a hold. Checkout asks the customer to reduce the quantity; the scenario ends.
A2 · Step 4: response lost
Checkout repeats the identical request with the same key. Inventory returns the original result, not a second hold; resume at step 4.
A3 · Before payment: hold expires
Checkout requests a new hold before proceeding. If stock is no longer available, follow A1; the expired hold cannot be confirmed.
