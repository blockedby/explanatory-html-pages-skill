Define the boundary before the payload

This fictional contract connects a checkout client, the Orders service and a fulfilment subscriber. Orders owns order identity and acceptance; fulfilment owns warehouse execution. A successful submission means an order is recorded, not that a parcel has shipped.

The example assumes authenticated service calls and an outbox stored in the same database as the order. It does not prescribe a particular broker or deployment platform. Those choices should not change the externally visible meaning of acceptance.

Submit an order

POST /v1/orders requires a caller-scoped Idempotency-Key. The server derives the customer identity from the authenticated caller rather than trusting an arbitrary customer ID in the body.

  "items": [{ "sku": "NOTEBOOK-A5", "quantity": 2 }]

A valid first submission returns 201 and a representation of the order. A replay returns the stored result. Invalid fields produce 422; reusing a key with a different normalized payload produces 409. An unauthenticated caller receives 401 before the operation is considered.

Persistence and publication are different boundaries

The database transaction protects the local invariant: an accepted order has an event waiting to be published. It does not make a distributed transaction out of the database and the broker. The publisher may send the same event again after losing an acknowledgement.

Consumers receive an event, not a command to repeat blindly

The consumer commits its duplicate marker and local work together before acknowledging delivery. Deduplication protects effects only if it shares the same transaction as those effects; writing a marker first and crashing before the work would lose the operation.

Recovery is part of the contract

Client timeout
Retry the same request with the same key. A new key expresses a new operation and can create another order.
Broker unavailable
Keep the outbox record and retry publication with backoff. Monitor age as well as queue length.
Duplicate event
Return the previously committed local outcome without creating duplicate warehouse work.
Poison event
Stop automatic retries after the configured budget, retain evidence and alert an owner. Do not quietly discard it.
Retention is an explicit assumption

This example assumes a 24-hour request-key retention window and a seven-day consumer deduplication window. Production values depend on actual retry and replay policy. A replay beyond a deleted deduplication record may create another effect, so retention must be coordinated with the operational replay procedure.

Acceptance checks target observable effects

  1. Two concurrent submissions with the same caller, key and payload produce one order.
  2. The same key with a changed quantity returns a conflict and leaves the original order unchanged.
  3. A crash after database commit but before the response can be recovered by replaying the key.
  4. A broker outage leaves accepted orders with pending outbox records and a visible operational signal.
  5. Redelivering an event produces one fulfilment effect, including a crash between processing and acknowledgement.

These are specification examples, not claims about a tested production service. Before adopting the contract, choose ownership, retention and error budgets that match the actual system.
