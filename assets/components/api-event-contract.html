Reservation API and creation event

This illustrative contract separates a synchronous outcome from asynchronous delivery. Receiving an event is not required before checkout can use the API response.

Create a hold · POST /v1/reservations

Caller and authorization
Checkout uses a service access token with inventory:reserve. Inventory derives the owning client from the token, not from the JSON body.
Input
Content-Type: application/json; required fields sku (nonempty case-sensitive string) and quantity (integer 1–100). Unknown fields are rejected.
Idempotency
Required Idempotency-Key is scoped to client and endpoint. Completed outcomes are retained for 24 hours. Identical retries replay the status and body; changed input returns 409 idempotency_conflict. Concurrent duplicates wait for the first result.
Retry
On a lost response or a 503, retry with the same key and payload using bounded exponential backoff. A replay does not renew the ten-minute hold; inspect its expiry before payment.
{"sku":"SKU-42","quantity":2}
Response outcomes
HTTP statusMeaningCaller action
201Hold committed; body below.Continue to payment before expiry.
400invalid_request; malformed input or missing key.Correct the request; do not retry unchanged.
401 / 403Invalid credentials / missing scope.Repair service authentication or permissions.
404unknown_sku.Refresh the basket item.
409insufficient_stock or idempotency_conflict.Reduce quantity or resolve key reuse; do not blindly retry.
503temporarily_unavailable; outcome may be unknown to the caller.Retry with the same key to discover the committed outcome.

Successful response:

{"reservation_id":"rsv_1042","state":"active","expires_at":"2026-05-01T10:10:00Z"}

Domain errors use a stable machine code and a human-readable message:

{"code":"insufficient_stock","message":"Only one unit is available."}

Event · inventory.reservation.created.v1

Producer → consumer
Inventory → checkout projection, through an authenticated broker topic restricted to these services.
Publication
The hold and outbox entry commit together. The publisher retries until the broker acknowledges delivery.
Delivery
At least once; duplicates and delayed messages are possible. Consumers deduplicate by event_id and must not treat a delayed creation event as proof the hold is still active.
Compatibility
Consumers tolerate unknown additive fields. Changing the meaning or type of existing fields requires a new event version.
Failure handling
After five failed consumer attempts, quarantine the message for inspection and replay with its original event ID; alert the checkout service owner.
