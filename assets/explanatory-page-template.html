01Start with one message

Request

What is a web request?

A web request is a message that asks another computer to do something or return something.

A browser creates the message. The message names a destination and an action, such as reading an order or saving a profile change. A response comes back with a result and enough information for the browser to show what happened.

Input
Method, destination, and optional data.
Work
Routing, rules, and state access.
Output
A status, result, and response data.
02See the relationship

Start with the path.

A request crosses boundaries. Each boundary has a different job, so follow the message rather than treating “the server” as one mysterious box.

Simplify on purpose.

Real systems may add caches, queues, identity services, or more databases. Start with the few boundaries that explain the reader’s question, then add detail only when it changes the decision they need to make.

03Unpack the mechanism

One exchange, step by step.

The same four boundaries become easier to reason about when each step has one verb and one owner.

  1. 01Browser

    Describe the job

    The browser packages the action as a method, destination, headers, and optional body.

  2. 02Edge

    Find a route

    The edge layer identifies where the request should go and may reject or cache it.

  3. 03Application

    Make a decision

    The application authenticates, validates, and chooses the work needed for the request.

  4. 04Database

    Return state

    The database supplies or records durable state; the application turns it into a response.

See the same exchange in plain English

A small example

A person opens an order page. The browser sends GET /orders. The application checks the session, asks the database for the person’s orders, receives the records, and sends back a response. The browser uses that response to render the page. A failed check or unavailable dependency changes the response at the boundary where it occurs.

04Keep responsibilities distinct

Each boundary answers a different question.

A useful diagram is not only a path. It also tells the reader what each participant owns and what it should not be asked to decide.

Responsibilities along the request path
Boundary Question it answers Typical responsibility
Browser What does the person need to see? Starts the request and renders the response.
Edge Where should this request go? Routes traffic and can reject or cache it.
Application Is the action allowed, and what follows? Applies rules and coordinates work.
Database What durable state exists? Stores and retrieves records.
05Take the model with you

Why draw the boundaries?

Boundaries make causes visible. When something is slow, rejected, or missing, the path suggests where to look instead of making every problem sound like “the network.”

01

Follow the message

Ask what was sent, where it went, and what came back. This keeps an explanation anchored to observable events.

02

Name the owner

Give each action a boundary. Clear ownership turns a large system into a sequence of smaller questions.

03

Add detail with a reason

Introduce a cache, queue, or extra service only when it explains a behavior the reader needs to understand.

Keep this model

A request is a message crossing boundaries. Each boundary can validate, route, change, or return it. That is enough of a map to choose the next useful question.
