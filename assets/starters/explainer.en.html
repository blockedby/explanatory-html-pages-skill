Start with the boundary

A service accepts a request, checks whether the action is allowed, and returns a result. Separating these responsibilities makes failures easier to explain: an unavailable dependency is not the same thing as a rejected request.

Working model

Follow one request from its caller to the owner of the data. Add another component only when it changes the explanation.

Trace one complete exchange

  1. The caller sends the information required for the action.
  2. The service validates the request and applies the relevant rules.
  3. The service returns a result that distinguishes success from rejection or temporary failure.
Where this model stops

Retries, asynchronous work and partial failures require additional rules. Describe them when they affect the reader's question, rather than treating every system as one identical request path.
